# git / GitHub の使い方

`CLAUDE.md` の Riot 規約と違い、これはプロジェクト運用上のルール。

## コミットの粒度

- 1コミット = 1つの論理的変更。機能追加・バグ修正・リファクタ・整形/コメント修正を混ぜない。
- 独立した変更はコミットを分ける。まとめる場合は本文に変更点を箇条書きで列挙する。
- 件名は簡潔な命令形＋接頭辞（`fix:` / `chore:` / `ci:` など）で、何を・なぜ変えたか分かるようにする。

## PR の粒度

- 1 PR = 1つの関係する変更。目的の異なる変更を1つの PR にまとめない。
- 「関係する」かどうかは変更箇所ごとではなく、**レビュアーが1つの話として読めるか**で判断する。
  同じ対象の同じ問題を調べる過程で見つかった付随修正は、同じ PR に入れてよい。
- 迷ったら「あとで revert するとき、片方だけ戻したくなるか」で考える。
  常に両方まとめて戻すことになる変更は、1つにまとめてよい。
- 依存更新・機能追加・CI 設定・ドキュメント修正などは、互いに独立していれば PR を分ける。
- 分けるとレビューが読みやすくなるだけでなく、問題があったときに revert する単位が小さくなる。
- 片方だけをマージすると壊れる場合は、必ず1つの PR にまとめ、本文に依存関係を明記する。

## リポジトリに残すものに書かない情報

- **Claude Code のセッション URL / セッション ID を書かない。**
  対象はコミットメッセージ・PR タイトル/本文・PR コメント・コード内コメントなど、
  リポジトリや GitHub 上に残るものすべて。public リポジトリなので内部識別子が
  公開されるうえ、読み手にとっての価値がない。
- ツールが PR 本文に**自動で付与した署名行**にもセッション URL が入ることがある。
  PR を作成・更新したら本文を読み返し、入っていれば消す。
- `@dependabot ...` のようなボットのコマンド文字列を、説明のつもりで本文に
  そのまま書かない。実際のコマンドとして解釈されうる。設定ファイルでの
  指定方法を案内するか、コマンドと読めない書き方にする。
